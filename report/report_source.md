## 1. Introduction

Autonomous robotic systems that can perceive their environment, plan paths, and cooperate with other agents are central to modern robotics research. This project implements two integrated intelligent robotic systems using Webots R2025a simulation and Python 3.13.

**Component A** implements a single autonomous mobile robot equipped with LiDAR and a camera. The robot builds an occupancy grid map, plans a collision-free path using Dijkstra's algorithm and A\*, and follows the path using a PID controller.

**Component B** implements a cooperative swarm of three autonomous robots. The robots communicate via Webots Emitter/Receiver devices, reach shared consensus on task state, allocate targets using Particle Swarm Optimisation (PSO), and navigate using a trained neural network classifier.

The project demonstrates the complementary roles of deliberative planning (Component A) and distributed emergent behaviour (Component B) in autonomous systems.

## 2. Methodology

### Simulation Environment

All robotic simulation uses Webots R2025a. Python 3.13 controllers run within the Webots process via the official `controller` module. Offline algorithm development, testing, and visualisation use pure Python with NumPy, Matplotlib, OpenCV, and scikit-learn — none of which depend on Webots.

### Experimental Design

Offline experiments are fully reproducible: all random seeds are fixed (seed = 42), and all datasets, figures, and metrics are saved automatically. Results reported in this document were generated by running `run_component_a.py` and `run_component_b.py` on the development machine (Windows 11, Python 3.13.5, Intel CPU).

Webots simulations must be run manually by opening the world files in Webots. Controller logs are saved to CSV/JSON for post-hoc analysis.

### Separation of Concerns

Each module has a single responsibility (configuration, grid, planner, controller, evaluation). This makes the code testable offline without Webots, while retaining full integration when Webots is available. A total of 109 automated unit tests verify correctness of all core algorithms.

```

        |
  PerceptionPipeline  <-- LidarScan, CameraFrame
        |
  SensorFusion  ---------> OccupancyGrid
        |
  PathPlanner (Dijkstra / A*)
        |
  NavigationController (heading PID + speed PID)
        |

        |
  Webots Motor Commands
```

### Component B Architecture

```
Webots GPS + Compass -> AgentState (pose, consensus_val, target_idx)
        |
  Emitter/Receiver (ring topology)
        |
  ConsensusUpdate (average consensus)
  PSO TaskAllocation (offline) -> target assignment
        |
  NumpyMLP (5-input, [16,8], 4-output) -> action
        |
  Safety fallback (obstacle threshold override)
        |
  Webots Motor Commands
```

### Coordinate Conventions

- **World frame**: X points East (right), Y points North (up). Origin at arena centre.
- **Grid frame**: row 0 = maximum world-Y (top of map), col 0 = minimum world-X (left). Row formula: `row = floor((origin_y + height - wy) / resolution)`.
- **Heading**: measured from the +X axis, counter-clockwise positive (standard mathematical convention).

## 4. Component A — Perception, Path Planning and Control

### 4.1 Webots World

The Component A arena is a 10 m × 10 m flat floor enclosed by 0.5 m walls. Seven static box obstacles of varying sizes are placed throughout the arena. The robot starts at (−3.5, −3.5) and must reach the goal at (3.5, 3.5). A green goal marker is placed at the goal position.

The robot is a custom differential-drive model with:
- Two independently driven wheels (radius 33 mm, separation 104 mm).
- A 360° LiDAR sensor (360 samples, range 0.05–3.5 m, noise σ = 0.02 m).
- A 64×48 pixel forward-facing camera (60° FOV).
- GPS and Compass for ground-truth position (evaluation only).

### 4.2 Occupancy Grid

The grid has 100×100 cells at 0.10 m resolution, covering the full 10 m × 10 m arena. Cells are classified as **free** (0), **occupied** (1), or **unknown** (2).

Obstacle footprints from the world configuration are marked occupied, then inflated by 2 cells (0.20 m) to provide clearance. This ensures the planned path maintains safe distance from obstacle edges.

During Webots simulation, the grid is updated online using LiDAR ray-tracing: cells along each ray are marked free; the hit cell is marked occupied.

### 4.3 Path Planning: Dijkstra and A\*

Both planners use 8-connected movement. Diagonal corner-cutting is prevented. Costs: cardinal step = resolution × 1.0; diagonal step = resolution × √2.

**A\* heuristic:** Octile distance — admissible and consistent for 8-connected grids with diagonal cost √2:

$$h(n) = r \cdot \left(\Delta r + \Delta c + (\sqrt{2} - 2) \cdot \min(\Delta r, \Delta c)\right)$$

**Benchmark results** (5-run average, Python 3.13.5, Windows 11):

| Metric             | Dijkstra | A\*   |
|--------------------|----------|-------|
| Nodes explored     | 9 555    | 715   |
| Path length (m)    | 10.72    | 10.72 |
| Mean plan time (ms)| ~25      | ~2    |

Both algorithms find equally optimal paths (identical length). A\* explores 13× fewer nodes by directing the search toward the goal, demonstrating that heuristic guidance significantly improves efficiency without sacrificing optimality.

### 4.4 Differential-Drive Kinematics

For wheel radius r, wheel angular velocities ω_R and ω_L, and wheel separation L:

$$v = \frac{r(\omega_R + \omega_L)}{2}, \qquad \omega = \frac{r(\omega_R - \omega_L)}{L}$$

Pose update (Forward Euler, time step Δt = 0.032 s):

$$x(t+\Delta t) = x(t) + v \cos\theta \cdot \Delta t$$
$$y(t+\Delta t) = y(t) + v \sin\theta \cdot \Delta t$$
$$\theta(t+\Delta t) = \theta(t) + \omega \cdot \Delta t$$

### 4.5 PID Controller

Two PID loops are used: a **heading PID** regulating the heading error, and a **speed PID** regulating distance to the current waypoint.

Features: anti-windup (integral clamped to ±2.0), first-order derivative filter (τ_f configurable), output limit ±6.28 rad/s, heading angle wrapped to (−π, π].

**Tuning comparison** (90° heading step response, simulated):

| Gain set       | Kp  | Ki   | Kd   | SS Error |
|----------------|-----|------|------|----------|
| Under-damped   | 3.0 | 0.10 | 0.05 | ~0.8°    |
| Well-tuned     | 1.5 | 0.05 | 0.20 | ~0.1°    |
| Over-damped    | 0.5 | 0.01 | 0.50 | ~3.2°    |

The well-tuned gains provide the best combination of fast convergence and low steady-state error. The under-damped set shows overshoot; the over-damped set is slow to respond.

### 4.6 Sensor Fusion

LiDAR hits are fused with camera blob detections using evidence accumulation. LiDAR confidence weight = 0.9 (high precision range sensor); camera confidence weight = 0.6 (limited depth estimation). Camera detections reinforce existing LiDAR-occupied cells or tentatively flag unknown cells.

**Limitations:** No Bayesian log-odds update is implemented. Camera range estimation uses an angular-size heuristic which is approximate. Extrinsic calibration is assumed perfect.

## 5. Component B — Multi-Agent Swarm Robotics

### 5.1 Webots Swarm World

The Component B arena is 12 m × 12 m with three static obstacles. Five target locations are distributed across the arena. Three differential-drive robots (Robot 1 = red, Robot 2 = green, Robot 3 = blue) start at (−3, −3), (0, −3), and (3, −3).

All three robots run the same `swarm_controller.py` controller but identify themselves via `controllerArgs[0]` ("robot_1", "robot_2", "robot_3").

### 5.2 Agent Communication

Each robot has a Webots Emitter (broadcast, channel 1) and Receiver. Messages are JSON-encoded `AgentMessage` structs containing position, heading, target assignment, and consensus state.

**Topology:** Ring (robot_1 ↔ robot_2 ↔ robot_3 ↔ robot_1). Topology is enforced in software at the receiver by filtering messages to ring neighbours only.

**Stale message handling:** Messages older than 2.0 seconds are discarded. This prevents stale data from corrupting consensus after a robot stops transmitting.

**Distinction:** Communication is used to share information (distributed), but each robot makes its own local navigation decision. This is not centralised control.

### 5.3 Average Consensus

Each agent maintains a scalar state $x_i$ (shared estimate of remaining target count). Update rule (synchronous, ring graph):

$$x_i(k+1) = x_i(k) + \alpha \sum_{j \in \mathcal{N}(i)} \left(x_j(k) - x_i(k)\right)$$

**Convergence condition:** For a connected undirected ring with $\alpha = 0.3 < 1/\text{max\_degree} = 0.5$, the algorithm converges to $x^* = \frac{1}{n}\sum_i x_i(0)$.

**Experiment results:**

| Parameter        | Value  |
|------------------|--------|
| Initial values   | [1, 4, 7] |
| True average     | 4.0    |
| α                | 0.3    |
| Converged at     | iteration 3 |
| Final max error  | < 0.000001 |

Convergence was rapid due to the small swarm size (3 agents) and well-chosen α.

### 5.4 PSO-Assisted Task Allocation

PSO finds a robot-to-target assignment minimising total travel distance. Particle representation: a 3-dimensional real vector $x \in [0, 5)^3$ where $\lfloor x_i \rfloor$ gives the target assigned to robot $i$.

**Fitness function:**

$$f(x) = \sum_{i=1}^{3} d(\text{robot}_i, \text{target}_{\lfloor x_i \rfloor}) + \lambda \cdot \text{duplicates}(x)$$

where $\lambda = 5$ penalises duplicate assignments.

**Results** (30 particles, 100 iterations):

| Method  | Assignment | Total cost (m) | Duplicates |
|---------|-----------|----------------|------------|
| PSO     | [3, 1, 4] | 12.58          | 0          |
| Greedy  | [0, 2, 3] | 13.65          | 0          |

PSO found a 7.8% lower-cost assignment than greedy. Both produced zero duplicates.

### 5.5 Neural Network for Navigation

A fully-connected feed-forward network (NumpyMLP) classifies the navigation action from 5 sensor features.

**Input features** (all normalised to [−1, 1] or [0, 1]):
1. Front LiDAR distance / max_range
2. Left LiDAR distance / max_range
3. Right LiDAR distance / max_range
4. Goal bearing / π
5. Heading error / π

**Output classes:** 0 = Forward, 1 = Turn Left, 2 = Turn Right, 3 = Stop

**Architecture:** Input(5) → Dense(16, ReLU) → Dense(8, ReLU) → Dense(4, Softmax)

**Training:** Mini-batch SGD, learning rate 0.01, 200 epochs, batch size 32. Dataset: 2000 balanced samples (500 per class) from a rule-based teacher policy.

**Results:**

| Metric                         | NumpyMLP | scikit-learn MLP |
|--------------------------------|----------|------------------|
| Test accuracy                  | 95.50%   | 95.25%           |
| Train samples                  | 1 600    | 1 600            |
| Test samples                   | 400      | 400              |

Both models achieve comparable accuracy, validating the NumpyMLP implementation.

**Safety fallback:** If the normalised front distance falls below the obstacle threshold (0.3), the network output is overridden: the robot turns toward the side with more clearance. This prevents unsafe learned actions from causing collisions.

### 5.6 Centralised vs Distributed Comparison

| Criterion          | Centralised (greedy, full knowledge) | Distributed (PSO + communication) |
|--------------------|--------------------------------------|------------------------------------|
| Total cost (m)     | 13.65                                | 12.58                              |
| Duplicate targets  | 0                                    | 0                                  |
| Communication req. | None (central planner)               | Ring-neighbour broadcast           |
| Scalability        | Poor (O(n²) with more robots)        | Better (local decisions)           |
| Fault tolerance    | Single point of failure              | Degrades gracefully                |

The distributed PSO approach outperforms greedy centralised allocation in this scenario. The centralised approach has no communication overhead but cannot recover from planner failure.

## 7. Discussion and Ethical Considerations

### 7.1 Sensor Bias and Reliability

LiDAR sensors return inaccurate readings near reflective surfaces, at extreme angles, or in dusty environments. The simulation uses Gaussian noise (σ = 0.02 m) but does not model specular reflections or systematic bias. The camera pipeline assumes uniform lighting; real cameras produce variable images under different lighting conditions, potentially causing false-positive obstacle detections.

The training dataset was generated synthetically from a rule-based policy, not from real sensor observations. This introduces a **simulation-to-reality gap**: features that are easy to classify in simulation (perfectly consistent sensor readings) may be ambiguous in reality. The model's 95.5% accuracy is a simulation-only result and should not be extrapolated to real-world deployment without validation on real sensor data.

Class imbalance was addressed by using balanced stratified sampling. However, the synthetic data does not capture all possible environmental conditions. A robot deployed in a new environment may encounter sensor patterns absent from the training set, leading to misclassification.

### 7.2 Transparency and Explainability

The NumpyMLP network is a black-box classifier: its internal representations are not directly interpretable. The five input features were deliberately chosen to be physically meaningful (obstacle distances, goal bearing, heading error), which improves the likelihood that the model's decisions align with human intuition. Logging all sensor observations and predicted actions (as implemented in the swarm controller) supports post-hoc review.

However, accuracy alone does not demonstrate safe autonomous navigation. A 95.5% accurate model still misclassifies 4.5% of inputs. In a safety-critical environment, each misclassified action could cause a collision. The safety fallback (obstacle threshold override) mitigates this but does not eliminate risk. Human review of logged trajectories before deployment is essential.

Confidence estimates (softmax probabilities) are available from the model and could be used to trigger a fallback when the network is uncertain (e.g. max probability < 0.7). This is not yet implemented and represents a future improvement.

### 7.3 Safety-Critical and Shared Environments

The robots operate in a shared environment where collision with other robots, static obstacles, or dynamic objects (pedestrians, machinery) is possible. The following risks are identified:

- **Incorrect localisation:** GPS in Webots gives exact position, but real GPS is noisy indoors. Localisation error propagates to path planning and collision avoidance.
- **Unexpected motor behaviour:** Motor controllers may overshoot or oscillate with poorly tuned gains. Anti-windup and output limits are implemented to reduce this risk.
- **Unsafe learned actions:** The neural network may output a Forward action when an obstacle is directly ahead if the sensor features were previously unseen. The safety fallback addresses this specifically.

**Mitigations implemented:** output velocity limits (±6.28 rad/s), PID integral anti-windup, LiDAR-based safety stop, goal timeout. **Mitigations proposed (not implemented):** dynamic obstacle detection, emergency stop hardware, geofencing.

### 7.4 Fault Tolerance and Robustness

The swarm communication uses a best-effort broadcast. If a robot fails or loses connectivity:
- Its outgoing messages stop. Neighbours detect this via the 2-second stale message timeout and stop incorporating its state into consensus updates.
- Its assigned target becomes unattended. No replanning mechanism is currently implemented to reassign the target to another robot.
- Consensus may converge to a different value than the true average if an agent disconnects mid-run. This is a known limitation of static-topology consensus algorithms.

**Implemented fault tolerance:** stale message timeout, per-agent independent navigation (failure of one robot does not directly cause others to fail), neural network safety fallback.

**Proposed but not implemented:** watchdog timers, dynamic target reassignment, network partition detection.

### 7.5 South African Context

Deploying autonomous robotic systems in South Africa raises specific considerations:

**POPIA (Protection of Personal Information Act, 2013):** The camera sensor in Component A can capture images of people if deployed in a human-occupied environment. Under POPIA, processing personal information (including images from which a person could be identified) requires a lawful basis, transparency, and data minimisation. Any camera-based robot deployed in a workplace or public space in South Africa must comply with POPIA's conditions for lawful processing (see POPIA Part A, Chapter 3). The current system does not implement facial recognition, but the raw camera data should not be stored without a retention policy.

**Worker safety and human oversight:** The robot safety standards should align with the Occupational Health and Safety Act (OHSA, 85 of 1993), which requires employers to identify and mitigate hazards. Autonomous robots operating near human workers must be assessed for collision risk and equipped with proximity sensors, audible warnings, and physical emergency stops. The current simulation does not model these.

**Infrastructure reliability:** South Africa experiences frequent power outages (load shedding) and variable network connectivity. Battery-backed systems and offline fallback behaviours (defaulting to a safe stop when connectivity is lost) are essential for practical deployment.

**Unequal access to automation:** The introduction of autonomous robots in industries such as mining, agriculture, and logistics may displace unskilled workers disproportionately. Responsible deployment includes skills development programmes and engagement with affected communities, as encouraged by the National Development Plan and the Presidential Commission on the Fourth Industrial Revolution.

**Accountability:** When an autonomous system causes harm, accountability must be clearly assigned — to the system designer, operator, or deploying organisation. This is not yet resolved in South African law, though general liability principles under the Law of Delict apply. Clear audit trails (such as the logs generated by this system) support post-incident investigation.

## 8. Conclusion and Recommendations

This project successfully implemented both components of the intelligent autonomous robotics assignment:

**Component A** demonstrated that an occupancy-grid-based architecture combining LiDAR perception, A\* path planning, and PID control can produce reliable autonomous navigation. A\* outperformed Dijkstra computationally (13× fewer nodes explored) while finding equally optimal paths. The PID controller converged to within 3.4° heading error with well-tuned gains.

**Component B** demonstrated that a three-robot swarm can cooperate effectively through ring-topology consensus, PSO-assisted task allocation (7.8% lower cost than greedy), and neural-network-guided navigation (95.5% accuracy). The distributed approach offers better scalability and fault tolerance than a centralised planner.

**Recommendations for future work:**

1. Implement a Bayesian log-odds occupancy grid update for more robust sensor fusion.
2. Replace the discrete PSO encoding with a purpose-built combinatorial optimisation method (Hungarian algorithm) for improved task allocation.
3. Add confidence-based fallback: trigger the safety fallback when the network's maximum softmax probability falls below a threshold.
4. Implement dynamic target reassignment when a swarm agent fails or times out.
5. Validate the system on a physical robot to quantify the simulation-to-reality gap.
6. Conduct a formal POPIA impact assessment before deploying camera-equipped robots in occupied spaces in South Africa.
